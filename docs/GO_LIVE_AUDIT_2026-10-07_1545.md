# Go-live audit: Stripe and readiness (2026-10-07)

**Checks:** 83/83 core tests pass. Typecheck is clean. The production build passes.

## Fixed in this pass
| Issue | Fix |
|---|---|
| A pro who was only *offered* a job could cancel it, raise its price, change its photos or get its payment link through the customer endpoints | All customer job actions now require `customer_id = signed-in user` (cancel, raise, counters, photos, pay, review, track) |
| A failure while applying a Stripe payment was silently lost (the retry was skipped as a duplicate) | It now raises a critical Hub alert, and a dispatch error no longer interrupts payment processing (the dispatch cron retries) |
| The webhook setup instructions left out `payment_intent.succeeded` (app payments) and the Stripe Identity events | Hub → Setup now lists every event the code uses |
| Open redirect on the language switch (`/api/lang?next=/\evil.com`) | Uses the shared `safeNext()` check |

## Fixed in the second pass (2026-10-07_1610): the "before real money" list
| Issue | Fix |
|---|---|
| Checkout links expired after 24h (invoices, balance emails) | Every link is now a permanent `/pay/<id>` that reopens Checkout, or creates a fresh one, for whatever is still owed |
| Paying an old link and a new one charged twice | Job payments reuse their open link. Any overpayment is refunded automatically and the job never counts more than its price |
| Remedy refunds hit only the deposit | Refunds now span every card payment (`refundAcross`). If one only partly goes through, a critical alert is raised |
| Refunds made in the Stripe dashboard were invisible | A `charge.refunded` handler updates `amount_refunded` (which feeds partner commissions, points and reports), turns off refunded gift cards, and alerts ops to review the pro's payout |
| A lost dispute didn't count as a refund, and repeated dispute events made duplicate deductions | Duplicate events are ignored. A lost dispute adds to `amount_refunded` |
| Payouts could be paid twice after a post-transfer error; the instant fee was kept when the instant payout failed; runs failed with insufficient balance | Only the transfer itself decides success. The instant fee is sent back when the instant payout fails. Weekly, partner and instant runs check the Stripe balance first. Idempotency keys are per attempt |
| No Stripe key: refunds "succeeded" silently | A critical "refund by hand" alert is raised |
| Paid bookings in ZIPs with no pro, and in ZIPs outside every market | These are no longer bookable and get a waitlist instead, with no payment taken. The waitlist emails people when a pro becomes available |
